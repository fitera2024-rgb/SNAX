# AGENTS.md — правила работы Codex в проекте SNAX

## 1. Перед началом любой задачи

1. Прочитай этот файл.
2. Прочитай `docs/SPEC.md`, соответствующий раздел `docs/TZ.md`, актуальные ADR и task card.
3. Проверь рабочее дерево и не перезаписывай чужие незавершённые изменения.
4. Сформулируй короткий план, список предполагаемых файлов и проверок.
5. При неоднозначном бизнес-решении не угадывай: зафиксируй вопрос в task/ADR и реализуй только согласованный вариант.

## 2. Неприкосновенные инварианты

- Ни одна строка файла не теряется молча.
- Raw-файл и raw-слой неизменяемы; повторная обработка создаёт новый run.
- 1С является источником истины для номенклатуры и подтверждённых связей.
- Сервис не рассчитывает потребность и не создаёт заказ поставщику.
- Прямой доступ к БД 1С запрещён.
- Макросы, external links и формулы Excel не исполняются.
- GTIN хранится строкой и не считается глобально уникальным.
- Fuzzy matching формирует кандидатов, но не утверждает связь.
- Все обмены и фоновые операции идемпотентны.
- Контракты и профили версионируются.
- Секреты и реальные коммерческие файлы не попадают в Git.
- Сервис может нормализовать документ поставки, но не проводит поступление и не изменяет складской остаток.
- Физический факт приемки принадлежит 1С и не заменяется результатом OCR.
- Магазин фиксирует факт в ограниченном рабочем месте и не получает избыточные права типовых документов.
- Неизвестный штрихкод сохраняется как исключение; молчаливое отбрасывание запрещено.
- Заказ, внешний документ, приемочная сессия и итоговый документ 1С должны быть прослеживаемо связаны.

Изменение любого инварианта допускается только отдельным ADR и одновременным изменением ТЗ/спецификации.

## 3. Границы модулей

- `domain` не импортирует framework/DB/file-reader модули.
- readers возвращают raw model, но не canonical items.
- normalization не открывает файлы и не пишет в БД напрямую.
- integration_1c работает только через канонические контракты.
- UI не реализует server-side бизнес-валидацию повторно.
- profile DSL — только декларативные данные; `eval`, произвольный код и shell запрещены.

## 4. Стиль изменений

- Делай маленькие, обозримые изменения в пределах одной task card.
- Не проводи попутный массовый рефакторинг.
- Не меняй публичный контракт без новой версии и contract tests.
- Не добавляй зависимость без обоснования и проверки лицензии/уязвимостей.
- Денежные и количественные значения — Decimal/NUMERIC и строки в JSON; не float.
- Время — timezone-aware UTC; отображение локализуется на краях системы.
- Ошибки имеют стабильный машинный код и локализуемое сообщение.
- Логи структурированы и не содержат секретов/полного коммерческого payload.

## 5. Тесты обязательны

Для каждого изменения добавь соответствующий уровень теста:

- чистая функция → unit/property;
- reader/profile → integration/golden;
- контракт → JSON Schema/OpenAPI contract test;
- DB → transactional integration;
- endpoint → API test;
- UI flow → component/e2e;
- 1С → модульный/интеграционный сценарий в тестовой базе.

Golden snapshot не обновляй автоматически. В PR объясни каждое смысловое изменение ожидаемого результата.

## 6. Безопасность файлов

- Применяй лимиты размера, листов, строк, колонок, времени и decompression ratio.
- Legacy XLS обрабатывай в изолированном worker без сети.
- Не запускай LibreOffice/Excel как часть production pipeline без отдельного ADR и sandbox design.
- Не доверяй расширению файла: проверяй MIME/signature.
- Не формируй object key из пользовательского пути.
- Не возвращай внутренний путь хранилища пользователю.

## 7. Работа с 1С

- Код 1С размещается в `onec-extension/` и документируется отдельно.
- Не изменяй типовую конфигурацию напрямую.
- Любая запись в типовые данные выполняется после staging и подтверждения.
- Остаток поставщика хранится отдельно от складского остатка.
- Повтор package ID не создаёт второй документ.
- ACK и mapping delta формируются только после сохранения результата транзакции.

## 8. Завершение задачи

Перед отчётом:

1. Выполни форматирование, lint, typecheck и релевантные тесты.
2. Проверь contract examples и миграции.
3. Проверь, что документация соответствует коду.
4. Покажи список изменённых файлов.
5. Сообщи команды и фактический результат.
6. Укажи остаточные риски, допущения и следующее логичное действие.

Не заявляй об успехе, если проверки не выполнялись. Не скрывай failing tests.

## 9. Запрещено

- коммитить `.env`, токены, пароли и production fixtures;
- отключать тест/линтер вместо исправления причины;
- использовать broad `except Exception` без логирования и классификации;
- молча приводить ошибочное значение к нулю/пустой строке;
- автоматически связывать номенклатуру только по похожести текста;
- применять пакет напрямую к ценам/заказам без staging;
- менять схему БД вручную без migration;
- создавать второй расчёт потребности во внешнем сервисе.

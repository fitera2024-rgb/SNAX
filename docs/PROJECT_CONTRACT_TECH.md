# 2. Предмет поставки и не-цели

Наименование: **«SNAX — программа стабилизации данных, централизованного заказа, приёмки поставок и управленческого контура».**

Исполнитель (ООО «ФИТЭРА») создаёт и сопровождает до G7:

1. внешний сервис безопасной нормализации прайсов и документов поставки;
2. расширение 1С:УТ (staging, matching, apply, РМ приёмки, контролируемый обмен);
3. каталоги MDM / узлов / обменов / расширений и паспорта KPI;
4. пилоты заказа и приёмки, затем волну отчётности на сверенных источниках;
5. эксплуатацию: мониторинг, backup/restore, обучение, handover.

Не-цели первой волны без change request: замена 1С/кассы/БП; расчёт потребности и заказ во внешнем сервисе; автосоздание номенклатуры; OCR как факт приёмки или основание проведения; production BI до G1/G2; таможенный брокер и все франчайзинговые исключения; массовое подключение всех поставщиков до UAT пилота; TASK-036; виртуальный склад; сценарное планирование SCL-011; полная историческая миграция всех баз.

# 3. Неприкосновенные инварианты

Изменение любого пункта — только новый ADR **и** одновременная правка ТЗ/спецификации.

1. Ни одна строка файла не теряется молча.
2. Raw-файл и raw-слой неизменяемы; повтор — новый processing run.
3. 1С — источник истины для номенклатуры и подтверждённых связей.
4. Сервис не рассчитывает потребность и не создаёт заказ поставщику.
5. Прямой доступ к БД 1С запрещён.
6. Макросы, external links и формулы Excel не исполняются.
7. GTIN хранится строкой и не считается глобально уникальным ключом.
8. Fuzzy matching формирует кандидатов и не утверждает связь.
9. Обмены и фоновые операции идемпотентны.
10. Контракты и профили версионируются.
11. Секреты и коммерческие payload не попадают в Git.
12. Сервис не проводит поступление и не меняет складской остаток.
13. Физический факт приёмки принадлежит 1С и не заменяется OCR.
14. Неизвестный штрихкод сохраняется как исключение.
15. Заказ, внешний документ, сессия приёмки и документ 1С прослеживаемо связаны.
16. Сервис — спутник **только центральной УТ**; в региональные узлы пишет штатный обмен 1С.

Границы модулей: `domain` без framework/DB/readers; readers возвращают raw, не canonical items; normalization не открывает файлы и не пишет в БД напрямую; integration_1c только через канонические контракты; UI не дублирует server-side валидацию; profile DSL без `eval`/shell.

Деньги и количества — Decimal/NUMERIC и строки JSON. Время — timezone-aware UTC.

# 4. Архитектура

## 4.1. Корпоративная топология (ADR-004)

```text
                    ┌─ БП СНЭКС
Единая 1С:УТ 11 ────┼─ БП СНЭКС СИБИРЬ
        │           └─ Центральная 1С:Розница ── региональные узлы ── франчайзи
        ▲
        │ import-package / receipt-package / mapping-sync (HTTPS, polling)
        │
Сервис нормализации (спутник; нет прямого DB 1С)
        ▲
  XLS/XLSX/CSV прайсы, PDF/XML/EDI накладные
```

- корпоративный master — единая 1С:УТ 11 УК СНЭКС;
- БП получают контролируемую выгрузку из УТ;
- магазин работает автономно в локальной Рознице;
- утверждённые номенклатура, цены и связи идут в Розницу штатным обменом, не сырым файлом поставщика;
- BI читает сверенные витрины и не чинит НСИ;
- Frontol сосуществует до D-34;
- 14 расширений проходят disposition `keep / refactor / replace / retire` (D-37); «ПомощникЗакупок» не переносится as-is (CFG-005, R-26).

Статусы компонентов до выгрузок: `PLANNED | UNVERIFIED | VERIFIED | RETIRED`.

## 4.2. Гибрид сервиса и 1С (ADR-001)

Сервис владеет: оригиналом и SHA-256; readers; версиями профилей; raw-слоем и transformation audit; нормализацией и DQ; каноническим пакетом; техническим мониторингом; кэшем связей из 1С.

1С владеет: внутренней номенклатурой и GUID; окончательными соответствиями; решениями «новинка / не работаем»; ценами после подтверждения; продажами, остатками, резервами, товаром в пути; расчётом потребности; заказом поставщику; проведением поступления; аудитом КМ.

## 4.3. Очередь (ADR-003)

PostgreSQL — источник истины. Import lifecycle, `ProcessingRun` и `OutboxMessage` создаются в одной транзакции. Dispatcher: `FOR UPDATE SKIP LOCKED`, публикация в Redis вне DB-транзакции. Celery — JSON-only at-least-once, очередь `snax.import.processing.v1`. Exactly-once эффект ограничен lifecycle БД (уникальность, lease token, optimistic version), не обещается для произвольных внешних side effects. Повтор обработки — новый immutable run. Durable dead-letter в PostgreSQL.

## 4.4. Стек сервиса

Python 3.12, FastAPI, Pydantic 2, SQLAlchemy 2, Alembic, PostgreSQL 16+, Celery+Redis, MinIO/S3, openpyxl `read_only/data_only` для XLSX, изолированный BIFF-worker для XLS, React+TypeScript UI без бизнес-валидации. SQLite только local developer mode.

Инфраструктура: ingress, API, worker, PostgreSQL, Redis, object storage, мониторинг, secret store, backup, сетевой маршрут до 1С или polling из внутреннего контура.

# 6. Конвейер файла поставщика

1. `POST /imports` — multipart, Idempotency-Key, сохранение в object storage, SHA-256, MIME/signature, лимиты размера/листов/строк/колонок/времени/decompression.
2. Object key формирует сервис, не пользовательский путь. Внутренний путь хранилища пользователю не возвращается.
3. Reader → `raw-workbook`: Workbook/Sheet/Row/Cell, 1-based индексы, A1, hidden/merged, `formulaText` + cached value **без исполнения**. `FORMULA` не запускается. `ERROR` хранит Excel-token в `rawValue` и machine `errorCode`.
4. Профиль — декларативный YAML по схеме, без произвольного кода. Дрейф шапки → `PROFILE_REVIEW`, старый профиль молча не применяется (IMP-014).
5. Классификация строк: PRODUCT, CATEGORY, HEADER, TOTAL, COMMENT, BLANK, DERIVED, ERROR.
6. Нормализация чистыми функциями + transformation events.
7. DQ: дубли, обязательные поля, цена, упаковка, ключи, GTIN.
8. `import-package` с digest, summary, rows, issues, audit. Decimal-строки.
9. 1С: staging (TASK-020) → matching (TASK-021) → apply (TASK-022) → типовой расчёт и черновик заказа (TASK-023).

`stableRowId` = `source_file_sha256 + sheet_name + row_number + selected_raw_cell_hash`. Товарный ключ — `externalVariantKey` в контексте поставщика, не глобально.

Сущности сервиса: `supplier`, `supplier_profile_version`, `source_file`, `import_batch`, `processing_run`, `raw_sheet/row`, `normalized_item`, `item_gtin/packaging/price/availability`, `import_issue`, `transformation_event`, `mapping_cache`, `export_package`, `delivery_attempt`, `outbox_event`, `audit_event`.

# 7. Сопоставление (matching)

Детерминированные ступени в 1С (сервис даёт данные, не утверждает GUID):

| Ступень | Результат |
|---|---|
| 1. Сохранённая связь `(supplier, externalVariantKey)` | `MATCHED_SAVED` либо review при смене критичных полей |
| 2. Код поставщика + упаковка | Только в контексте поставщика; глобальный поиск артикула запрещён |
| 3. GTIN + упаковка | `MATCHED_EXACT` при одном кандидате и совместимой упаковке |
| 4. Устойчивый код без GTIN | Первая связь требует подтверждения |
| 5. Ранжирование кандидатов | Score сохраняется; порог не делает `APPROVED` |
| 6. Нет кандидата | `NEW_ITEM` / заявка / `DO_NOT_BUY` |

Неизвестный коэффициент упаковки — блокирующий `PACKAGING_CONFLICT`. Mapping version: 1С побеждает при конфликте (INT-008).

# 8. Приёмка (ADR-002, TZ addendum v2.1)

TO-BE: заказ в 1С → (опционально) `receipt-package` → связь с заказом → магазин сканирует в ограниченном РМ → неизвестное в exception → товаровед проводит типовой документ. OCR — подсказка с confidence, не факт и не проведение.

Маршруты: `DIRECT_TO_STORE`, `CENTRAL_WAREHOUSE`, `RECEIPT_AND_TRANSFER`; `CROSS_DOCK` вне первой волны без отдельного решения. Точный типовой документ — D-11/D-12.

Источники истины: файл — сервис; заказ, номенклатура, связь, отсканированное количество, проведение, остаток — 1С.

Статусы пакета приёмки: `RECEIVED → PROFILED → PARSED → PUBLISHED → IMPORTED_1C → LINKED_TO_ORDER → IN_ACCEPTANCE → SUBMITTED → APPROVED → POSTED`. Альтернативы: `DUPLICATE_DOCUMENT`, `PARSING_REVIEW`, `BLOCKED`, `REJECTED`, `CANCELLED`.

Статусы строки: EXPECTED, MATCHED, SCANNED, SHORTAGE, OVERAGE, UNPLANNED_ITEM, MAPPING_REQUIRED, MULTIPLE_MATCHES, PACKAGING_CONFLICT, PRICE_MISMATCH, DAMAGED, REJECTED, ACCEPTED.

Магазин не проводит закупку и не получает лишние права типовых документов. Повтор SHA-256 того же поставщика → `DUPLICATE_DOCUMENT`.

# 10. Выгрузки информационных баз

Носители: `*.cf` / `*.cfe` / XML конфигурации; `*.dt` тестовой копии; реестр расширений; обезличенные логи обмена; PDF-протоколы как evidence, не как истина. Не выгрузка: прайс (import-package), УПД (receipt-package), `.env`.

Передача: хранилище вне Git + `manifest.json`. В репозиторий — только манифест/checksums. Разбор на изолированной TEST-машине.

Обязательные поля манифеста: `schemaVersion`, `intakeId`, `receivedAt`, `sourceOwner`, `classification`, `gitPolicy=DO_NOT_COMMIT_PAYLOAD`, `bases[]`, `artifacts[]` (fileName, mediaType, sha256, sizeBytes, kind), период среза, sanitization, `intendedUse`.

Состояния: `RECEIVED → QUARANTINE_SCAN → REGISTERED → PARSED_CATALOGS → VERIFIED → ARCHIVED`. Альтернативы: `REJECTED_POLICY`, `BLOCKED_SECRETS`, `PARTIAL`.

Нельзя: DT/CF в Git; логировать полный payload; production credentials в CI; перепроводить рабочую базу; отключать расширения до инвентаризации (R-25); грузить дамп в PROD.

Acceptance DI-AC-001…006: schema, идемпотентность SHA-256, чистое дерево Git, статус каждой базы, сверка 14 расширений, нет секретов в манифесте.

# 11. Доменные правила (реестр v1.2)

## 11.1. Управление — GOV-001…012, CFG-001…010

Единый backlog WORK/TASK; decision log; среды DEV/TEST/UAT/PROD; backup/rollback до массовых операций 1С; не кодировать неутверждённые правила. D-29: GitHub Actions не стартует из‑за billing — это не дефект кода. D-30: stacked PR WORK-006…009.

## 11.2. НСИ — MDM-001…012

Таблица соответствий магазин—подразделение—склад—касса—организация—регион—узел. До дампа каталог `UNVERIFIED` с пустыми GUID. Упаковки/MOQ — D-03.

## 11.3. Обмены — INT-001…010, ARC-010

Документ либо проведён, либо в очереди исключений. Контроль: найдено / выгружено / записано / проведено / ошибка, checksums, retry, SLA. Запись без проведения не есть успешная загрузка.

## 11.4. Закупки — ORD-001…012, PRC, INV

Заказ создаёт категорийный блок, не магазин. Расчёт — типовой механизм УТ. Сервис заканчивается на `import-package`. Исключения КМ: нет mapping, новинки, blocking DQ, цена/упаковка, нулевая рекомендация.

## 11.5. Финансы — FIN-001…018

Не реализуется во внешнем сервисе. Запрет технических закрытий отрицательных остатков. Ворота закрытия месяца. Полная себестоимость и P&L по начислению с drill-down. Казначейство — D-24.

## 11.6. Продажи — OPS, SAL

Факт продажи (OPS-002, D-44): проведённый документ без отгрузки/чека не выручка. Жизненный цикл клиентского заказа — 1С/CRM.

## 11.7. BI и масштаб — BI, SCL

Официальный срез показывает состав точек и freshness; неполный срез не выдаётся за полный (R-30). Платформа BI — D-25. Чек-лист новой точки не стартует до G1/G2 (R-29).

# 12. Расширение 1С

Код только в `onec-extension/`. Типовая конфигурация не снимается с поддержки. Запись в типовые объекты — после staging и подтверждения. Остаток поставщика хранится отдельно от складского остатка. Повтор package ID не создаёт второй документ.

Критические расширения первичного анализа: `пр_НоменклатураРасширенныйПремиум`, `ПомощникЗакупок` (закрытый код, собственные данные). Не отключать до инвентаризации.

# 13. Состояния импорта (сервис)

`RECEIVED` → `DUPLICATE` | `PROCESSING` → `PROFILE_REVIEW` | `VALIDATED` | `BLOCKED` | `ERROR` → `READY_FOR_1C` → `DELIVERED` → `ACCEPTED_BY_1C` | `REJECTED_BY_1C` → `ARCHIVED`.

1С staging: `NEW → LOADED → MATCHING → READY_TO_APPLY → APPLIED | PARTIAL | REJECTED | CANCELLED | ERROR`.

# 14. Нефункциональные требования

ТЗ v2.0 NFR-001…016: прослеживаемость; нет молчаливых потерь; идемпотентность; p95 5 000 строк ≤ 180 с; ≥ 100 000 строк/сутки; UI p95 ≤ 2 с; доступность 99,5% после MVP; безопасность файлов; TLS и минимальные права; аудит; observability; backup; среды; профили без релиза ядра; качество кода; UI на русском, коды ошибок стабильные английские.

Приёмка NFR-RCV-001…010: отклик скана ≤ 1 с локально / ≤ 3 с удалённо; сканы не теряются при обрыве (офлайн — отдельное решение); идемпотентность; нет прямого DB 1С; Decimal/строки; шифрование транспорта; нет полного payload в логах; срок хранения по учётной политике; ≥ 2 000 строк поставки; machine code + русское сообщение + correlation ID.

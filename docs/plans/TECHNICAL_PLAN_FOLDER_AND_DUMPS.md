# Технический план SNAX: работа с папкой файлов и выгрузками баз

| Поле | Значение |
|---|---|
| Статус | рабочий план обследования и первой волны реализации |
| Дата | 27 августа 2026 |
| Базовый контракт | ТЗ v2.0, SPEC v2.0, дополнение 2.1 по приемке, ADR-001…003 |
| Владельцы | tech lead сервиса, архитектор 1С, product owner |
| Область | что можно сделать **без прямого доступа к живой БД 1С**, имея папку исходных файлов и выгрузки информационных баз |

Документ не заменяет ТЗ и SPEC. Он отвечает на практический вопрос: какие технические результаты можно получить из уже доступных материалов, какие работы разблокируются сразу, а что по-прежнему требует тестовой базы 1С, бизнес-решений и живого обмена.

## 1. Допущения о составе доступа

Пока состав папки и формат выгрузок не зафиксированы отдельным инвентарём, план исходит из двух рабочих гипотез. Если фактический состав уже, часть шагов сжимается; если шире — расширяется только внутри той же границы ответственности.

### 1.1. Папка файлов

Ожидаемый минимум:

- прайс-листы и бланки заказа поставщиков (`XLS`, `XLSX`, `CSV`);
- повторные версии тех же шаблонов, если они есть;
- при наличии — документы поставки: УПД, накладные, PDF/сканы, XML;
- служебные файлы обмена 1С, если они лежат рядом (`xml`, `txt`, `json`), но не как production-канал сервиса.

Это тот же тип корпуса, который уже обследован в ТЗ: 26 файлов, 22 уникальных SHA-256, 20 профилей, 4 937 товарных строк XLSX.

### 1.2. Выгрузки баз

Ожидаемый минимум по контурам, которые реально участвуют в заказе и приемке:

| Контур | Зачем нужна выгрузка |
|---|---|
| 1С:УТ (закупки, номенклатура, склады, заказы) | D-01, matching, пилот расчёта, маршруты приемки |
| 1С:Розница / обмен УТ↔Розница, если используется | понять, где живёт факт магазина и штрихкоды |
| Бухгалтерия — только метаданные обмена | не для заказа, а чтобы не сломать межбазовый контур |

Предпочтительные форматы, в порядке убывания практической пользы:

1. полная копия информационной базы (`.dt`) **для изолированного тестового контура**;
2. выгрузка конфигурации и расширений (`.cf` / `.cfe`) — релиз, объекты, доработки;
3. табличные выгрузки справочников и регистров: номенклатура, штрихкоды, номенклатура партнёров, упаковки, склады, партнёры/контрагенты, способы обеспечения, открытые заказы поставщику;
4. XML/JSON отчёты или обработки выгрузки без SQL.

SQL-дамп таблиц 1С допустим **только как материал обследования**. Он не становится каналом интеграции: прямой доступ сервиса к БД 1С запрещён инвариантом ADR-001 и `FR-INT-015`.

## 2. Текущий baseline репозитория

На `main` уже есть каркас внешнего сервиса, но нет production-разбора файлов и нет расширения 1С.

| Слой | Состояние |
|---|---|
| Bootstrap, web shell, CI, Compose | WORK-001, в `main` |
| Регистрация файла, SHA-256, PostgreSQL, MinIO | WORK-002, в `main` |
| Очередь, outbox, worker, recovery | WORK-003, в `main` |
| Raw workbook model и Reader Protocol | WORK-004, в `main` |
| XLSX / XLS / CSV readers | ветки `work/005`…`work/007`, PR открыты |
| Profile schema / detection | ветки `work/008`…`work/009`, PR открыты |
| Normalization, DQ, package builder | backlog `TASK-013`…`TASK-015` |
| Пилотные профили и golden | `TASK-016`, ждут реальные файлы |
| API для 1С и mapping cache | `TASK-018`…`TASK-019` |
| Расширение 1С | `TASK-020`…`TASK-023`, каталог `onec-extension/` ещё не заполнен |
| Приемка | `TASK-026`…`TASK-036`, контракт `receipt-package` есть, кода нет |

Следствие: папка файлов сразу кормит волну readers/profiles/golden. Выгрузки баз сразу кормят обследование 1С и дизайн matching, но не позволяют сервису «подключиться к таблицам».

## 3. Правила обращения с материалами

Эти правила действуют до любой обработки.

1. Коммерческие файлы, `.dt`, `.cf`, цены, остатки и персональные данные **не коммитятся в Git**.
2. Рабочая копия лежит в защищённом хранилище вне репозитория. В Git — только обезличенные golden fixtures, схемы, контрольные суммы и отчёты без payload.
3. Для каждого исходника фиксируются: путь, размер, SHA-256, MIME/signature, дата получения, контур (файл поставщика / УТ / Розница / документ поставки).
4. Excel не открывается как исполняемый документ: макросы, внешние ссылки и формулы не запускаются.
5. Повторная обработка файла создаёт новый run и не перезаписывает оригинал.
6. Выгрузка базы восстанавливается только в изолированную тестовую ИБ. Production не монтируется и не обновляется этим планом.
7. Результаты обследования, которые содержат коммерческие значения, хранятся рядом с исходниками; в репозиторий уходят агрегаты, доли покрытия и технические выводы.

Рекомендуемая раскладка вне Git:

```text
secure-data/
├── inventory.md
├── files/
│   ├── suppliers/<supplier>/<yyyy-mm-dd>/<original>
│   └── receipts/<yyyy-mm-dd>/<original>
├── dumps/
│   ├── ut/<date>/<dt-or-export>
│   ├── retail/<date>/...
│   └── config/<date>/*.cf*
├── derived/
│   ├── fingerprints/
│   ├── nomenclature-stats/
│   └── match-coverage/
└── golden-candidates/   # ещё не обезличенные кандидаты в fixtures
```

## 4. Что можно сделать по папке файлов

Это независимый контур внешнего сервиса. Живая 1С для него не нужна.

### 4.1. Инвентаризация корпуса

- полный каталог файлов: имя, размер, SHA-256, сигнатура, расширение vs MIME;
- дедупликация точных копий;
- группировка по поставщику и версии шаблона;
- выделение legacy XLS отдельно от XLSX/CSV;
- сверка с уже описанным корпусом ТЗ (20 профилей, в том числе ОПТ24, ОПТ1/ОПТ2, Сабитов, Суфлет/SOJ, ИП Вагабова).

Результат: `inventory.md` + таблица «файл → кандидат профиля → аномалии».

### 4.2. Structural fingerprint без бизнес-логики

После WORK-005…007 каждый файл читается в raw workbook:

- имена и порядок листов;
- строка шапки (1–16 по ТЗ);
- merged ranges, скрытые листы, формулы и cached values;
- `#REF!` и прочие error tokens;
- повторные шапки, категории, итоги;
- счётчики строк/колонок/ячеек.

Это закрывает reader-часть `AC-001…AC-009` ещё до профилей: ни одна строка не должна теряться молча.

### 4.3. Черновики профилей пилота

По 3–5 контрастным файлам, а не по всем 20 сразу:

1. простой однотабличный XLSX;
2. многолистовой файл с повторными шапками;
3. файл с несколькими единицами заказа;
4. файл с ценовой лестницей и статусом наличия;
5. файл со сломанными формулами / derived sheet.

Для каждого профиля фиксируются: листы-источники, aliases колонок, классификация строк, правила GTIN, упаковки, цены, blocking checks. Произвольный код в профиле запрещён.

### 4.4. Обезличенные golden fixtures

Из реальных файлов строятся Git-безопасные копии:

- структура, аномалии и типы значений сохраняются;
- наименования, цены, количества и коммерческие коды заменяются синтетическими эквивалентами;
- ожидаемые `summary/rows/issues` утверждаются отдельно и не обновляются автоматически.

Без этой папки `TASK-016` остаётся на demo-профиле. С папкой пилот становится проверяемым.

### 4.5. Watch-folder как канал пилота

SPEC и ТЗ допускают поступление файла через выделенный каталог. Имея папку, можно спроектировать и позже реализовать:

- периодический ingest существующих файлов в уже готовый `POST /imports`;
- идемпотентность по SHA-256 и `X-Idempotency-Key`;
- статус `DUPLICATE_FILE` для точных копий;
- object key вида `raw/sha256/{digest[0:2]}/{digest[2:4]}/{digest}` без пользовательского пути.

Это не заменяет API 1С и не публикует пакет в учёт.

### 4.6. Чего папка сама по себе не даёт

- подтверждённых связей с номенклатурой SNAX;
- проверки упаковок и единиц 1С;
- расчёта потребности и черновика заказа;
- маршрута приемки и прав магазина;
- решения D-01 по релизу УТ.

## 5. Что можно сделать по выгрузкам баз

Это контур обследования 1С. Сервис по-прежнему не читает таблицы 1С в runtime.

### 5.1. Закрытие технического неизвестного D-01

Из `.cf/.cfe` и/или восстановленной тестовой ИБ:

- точный релиз УТ и режим поддержки;
- список существующих расширений;
- наличие типовых объектов: номенклатура партнёра, штрихкоды, упаковки, соглашения, обеспечение потребностей, заказ поставщику, поступление, перемещение;
- фактические доработки, которые нельзя затронуть;
- возможность расширения без снятия конфигурации с поддержки.

Результат: карточка совместимости 1С для `onec-extension/` и матрица объектов под `TASK-020`.

### 5.2. Качество master-data для matching

Табличные выгрузки достаточны, даже если полная `.dt` ещё не восстановлена.

Нужны срезы:

| Срез | Зачем |
|---|---|
| Номенклатура + единицы + характеристики | понять, что является внутренним SKU |
| Штрихкоды | оценить покрытие GTIN и дубли |
| Номенклатура партнёров / коды поставщика | есть ли уже связи, которые можно переиспользовать |
| Упаковки и коэффициенты | конфликты «штука/блок/короб» |
| Партнёры и договоры | ключ поставщика в 1С |
| Склады / магазины / организации | маршруты приемки |
| Способы обеспечения потребностей | пилот `TASK-023` |
| Открытые и недавние заказы поставщику | связь заказ → поставка |
| Регистр остатков и резервов — только статистика | не копировать в сервис как источник истины |

По каждому срезу считаются агрегаты, а не выгружается коммерческий payload в Git:

- доля номенклатуры с валидным GTIN;
- доля дублей GTIN и GTIN без контрольной цифры;
- доля позиций с заполненной номенклатурой партнёра;
- доля упаковок с коэффициентом ≠ 1;
- магазины без однозначного склада;
- поставщики пилота, которых нет в справочнике партнёров.

### 5.3. Дизайн matching на реальном распределении, не на гипотезе

SPEC уже задаёт ступени:

1. сохранённая связь;
2. код поставщика + упаковка;
3. GTIN + упаковка;
4. уникальный код в контексте поставщика;
5. fuzzy только как кандидаты;
6. новинка.

Выгрузки позволяют оценить, какая ступень будет основной на пилоте:

- если номенклатура партнёра заполнена — ступень 1/2 даст высокий автопокрытие после первой ручной волны;
- если штрихкоды качественные — ступень 3 даст `MATCHED_EXACT`;
- если GTIN дырявые или дублируются — автоподтверждение нельзя включать даже как черновик D-политики.

Fuzzy по названию по-прежнему **не утверждает** связь.

### 5.4. Пилот типового расчёта без второго ядра

На копии базы, не в сервисе:

- выбрать 30–50 контрольных SKU;
- зафиксировать фактические параметры обеспечения;
- сравнить типовой расчёт УТ с текущим Excel-шаблоном заказа;
- описать расхождения как бизнес-решение, а не как баг парсера.

Сервис для этого шага нужен только как поставщик нормализованных цен/упаковок после matching. Сам расчёт остаётся в 1С.

### 5.5. Обследование приемки

Из выгрузки УТ/Розницы:

- какой документ создаётся при прямой поставке в магазин;
- есть ли обязательный путь «поступление на РЦ + перемещение»;
- где живут штрихкоды, которые сканирует магазин;
- какие роли реально проводят поступление;
- есть ли серии, сроки годности, маркировка в пилотных категориях.

Это закрывает вход в `TASK-030…TASK-033` без угадывания маршрута.

### 5.6. Чего выгрузки сами по себе не дают

- безопасного runtime-доступа сервиса к 1С;
- права менять типовые объекты без staging и подтверждения;
- актуальных остатков как online-потока;
- OCR/EDI, если в папке нет структурированных документов поставки;
- утверждения ценовой политики и частичного применения пакета.

## 6. Что даёт совместный доступ: папка + выгрузки

Это главная ценность текущего окна доступа. Можно посчитать покрытие пилота до написания расширения.

### 6.1. Перекрёстный отчёт «внешняя позиция → номенклатура 1С»

Для каждого пилотного поставщика:

1. нормализовать файл сервисом (или временным offline-конвейером после readers);
2. построить `externalVariantKey` = поставщик + код + GTIN + упаковка;
3. сопоставить с выгрузкой 1С детерминированными ступенями 1–4;
4. отдельно пометить fuzzy-кандидатов ступени 5 без автоутверждения.

Итоговые доли:

| Корзина | Смысл |
|---|---|
| `MATCHED_EXACT` / точный GTIN+упаковка | оценка автопокрытия |
| уникальный код поставщика | кандидаты на первую ручную волну |
| несколько кандидатов | риск ложных связей |
| конфликт упаковки | работа master-data до пилота |
| нет ключа | ручной контур, нельзя терять строку |
| GTIN есть у нескольких поставщиков | подтверждение инварианта «GTIN не глобальный ключ» |

ТЗ уже фиксирует 238 нормализованных GTIN, встречающихся у двух и более поставщиков. Выгрузка 1С покажет, как эти коды представлены внутри SNAX.

### 6.2. Список контрольных SKU

Не абстрактные 30–50 позиций, а конкретный набор:

- есть в файле поставщика и в 1С;
- есть продажи/остаток в выгрузке;
- есть упаковка и штрихкод;
- плюс несколько конфликтных случаев: leading zero, один GTIN / две упаковки, `#REF!`, placeholder.

Этот список становится входом в `TASK-023` и UAT заказа.

### 6.3. Оценка трудозатрат КМ

По корзинам matching можно сказать, какой объём исключений увидит категорийный менеджер на первом цикле, не кодируя рабочее место 1С. Это проверяет цель BR-002 до разработки UI.

### 6.4. Файловый пилот обмена

Пока API 1С не готов, SPEC допускает единый XLSX/JSON-пакет и ручную загрузку внешней обработкой в копию базы. Совместный доступ позволяет:

- собрать канонический пакет из реального файла;
- загрузить его в тестовую ИБ обработкой;
- проверить идемпотентность повторного `packageId`;
- не трогать production.

## 7. Граница: что делать нельзя даже при полном доступе

| Запрещено | Почему |
|---|---|
| Подключать сервис к таблицам 1С | ADR-001, `FR-INT-015`, `AGENTS.md` |
| Считать потребность и создавать заказ во внешнем сервисе | BR-004, инвариант проекта |
| Автоматически утверждать связь по похожести названия | fuzzy только формирует кандидатов |
| Записывать остаток поставщика как складской остаток | отдельный регистр наличия |
| Исполнять формулы и макросы Excel | reader хранит formula text и cached value |
| Проводить поступление по результату OCR | факт приемки принадлежит 1С |
| Менять типовую конфигурацию вместо расширения | граница модуля 1С |
| Коммитить `.dt`, прайсы, УПД и цены | NFR-013 и политика секретов |
| Угадывать D-04…D-14 и маршрут приемки | фиксируется в ADR/task, не в коде |

Если для анализа удобно открыть SQL-дамп 1С, это разовое обследование. Канал интеграции после обследования остаётся: канонический пакет → staging 1С → ACK / mapping delta.

## 8. Последовательность работ

Работы идут двумя параллельными лентами. Сервис не ждёт полную восстановленную ИБ, 1С не ждёт все 20 профилей.

```text
Папка файлов                         Выгрузки баз
     │                                    │
     ▼                                    ▼
Инвентарь + SHA-256                  Карточка релиза УТ (D-01)
     │                                    │
     ▼                                    ▼
Readers 005–007                      Срезы master-data
     │                                    │
     ▼                                    ▼
Профили 008–011 + golden 016         Оценка matching 1–4
     │                                    │
     └────────── пересечение ─────────────┘
                      │
                      ▼
           Отчёт покрытия пилота
           3–5 профилей, контрольные SKU
                      │
          ┌───────────┴───────────┐
          ▼                       ▼
 Normalization/DQ/package     Каркас onec-extension
 TASK-013…015, 017            TASK-020…021
          │                       │
          └────────── пилот ──────┘
                файловый пакет → staging копии УТ
                затем API polling TASK-018
```

### Волна A — сразу по папке

1. Зафиксировать инвентарь и контрольные суммы; не копировать файлы в Git.
2. Довести readers до зелёных golden на синтетике, затем прогнать на реальном корпусе offline.
3. Выбрать 3–5 пилотных поставщиков совместно с КМ (вход в D-02).
4. Написать профили и обезличенные fixtures.
5. Собрать нормализованный пакет и протокол качества.

### Волна B — сразу по выгрузкам

1. Снять релиз, расширения и объекты УТ.
2. Посчитать качество GTIN, упаковок и номенклатуры партнёров.
3. Описать склады/магазины и кандидат маршрута приемки — без утверждения.
4. Подготовить состав тестовой ИБ: что маскировать, какие периоды резать, какие документы оставить.
5. Сформировать черновик метаданных расширения по фактическим именам объектов, а не по рабочим именам SPEC.

### Волна C — пересечение

1. Перекрёстный отчёт покрытия.
2. Список контрольных SKU и конфликтных кейсов.
3. Решение: файловый пилот или сразу HTTPS polling (D-03).
4. Первый task card на `onec-extension/` после D-01.

### Волна D — не стартует из этих материалов

- apply в типовые объекты без политики D-09/D-10;
- автоподтверждение `MATCHED_EXACT` без D-политики;
- OCR как источник факта;
- промышленный обмен с production-базой.

| Артефакт | Путь |

Вне репозитория:

- `inventory.md` с SHA-256;

Каждый Git-артефакт содержит дату среза, источник (`папка` / `выгрузка УТ` / `выгрузка Розницы`) и уровень доказательности: факт из файла, агрегат из выгрузки, гипотеза.

## 11. Минимальный запрос, если состав доступа ещё неполный

Если папка или выгрузки уже есть, но неполные, для плана достаточно следующего комплекта.

Из файлов:

- актуальные прайсы 3–5 кандидатов пилота, не обязательно все 20;
- хотя бы один legacy XLS, если он останется в MVP;
- один обезличенный или защищённо хранимый УПД на ~30 строк для приемки.

Из баз:

- `.cf` УТ + список расширений;
- таблица номенклатуры: код, наименование, единица, признак характеристики;
- штрихкоды: номенклатура, штрихкод, упаковка;
- номенклатура партнёров / коды поставщика;
- склады и организации;
- способы обеспечения и 1–2 заполненных настройки по пилотным SKU;
- при возможности — `.dt` для отдельной тестовой ИБ, без production-доступа.

Не требуется для старта волны A/B: online-остатки, банк, кассы, бухгалтерия, персональные данные сотрудников.

## 12. Критерий успеха этого окна доступа

Окно «есть папка и выгрузки» считается использованным, когда одновременно выполнено:

1. корпус файлов проинвентаризирован и не попал в Git;
2. 3–5 пилотных профилей имеют структурный fingerprint и план golden;
3. известен релиз УТ и состав объектов, которые затронет расширение;
4. посчитаны доли точного matching, конфликтов упаковки и строк без ключа;
5. выбран набор контрольных SKU;
6. сформулирован следующий WORK/TASK без угадывания D-решений;
7. зафиксирован запрет превращать дамп 1С в runtime-интеграцию.

Следующее логичное действие после этих семи пунктов — не «подключить базу к сервису», а закрыть D-01/D-02 с владельцами и открыть `TASK-016` плюс каркас `TASK-020` на копии УТ.

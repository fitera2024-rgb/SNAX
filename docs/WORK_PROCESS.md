# Процесс выполнения работ SNAX

## 1. Единица планирования

Каждое изменение выполняется как отдельная **работа** с номером `WORK-NNN`.

Обязательный паспорт каждой работы:

| Поле | Обязательно |
|---|---|
| Номер работы | Да |
| Название | Да |
| Репозиторий | Да |
| Базовая ветка | Да |
| Желаемая ветка публикации | Да |
| Issue | Да |
| Модель Codex | Да |
| Reasoning effort | Для GPT-5.3-Codex |
| Роль GPT-5.6 Pro | Да |
| Scope / out of scope | Да |
| Acceptance criteria | Да |
| Команды проверок | Да |
| Результаты проверок | При завершении |
| Остаточные риски | При завершении |

## 2. Именование веток

```text
work/NNN-kebab-case-name
```

Примеры:

- `work/001-web-bootstrap-impl`;
- `work/002-import-contracts`;
- `work/003-file-upload`.

Одна опубликованная ветка соответствует одной работе. Попутные несвязанные изменения запрещены.

## 3. Распределение ролей

### Codex

- реализует task card;
- выполняет проверки;
- сообщает фактический результат;
- создаёт локальный commit;
- публикует PR встроенным механизмом Codex Cloud;
- не принимает неописанные бизнес-решения.

### GPT-5.6 Pro

- формализует работу;
- проверяет соответствие ТЗ и ADR;
- выполняет отдельные изменения при необходимости;
- анализирует diff и тестовые доказательства;
- фиксирует замечания;
- подтверждает готовность к merge либо возвращает работу на исправление.

## 4. Выбор модели Codex

### GPT-5.3-Codex

Основная модель проекта. Назначается для:

- архитектуры и bootstrap;
- изменений нескольких модулей;
- backend и data model;
- миграций БД;
- readers и normalization;
- безопасности файлов;
- публичных API и контрактов;
- интеграции с 1С;
- сложной диагностики;
- финального прохода по работе.

Рекомендуемый reasoning:

- `medium` — локальная задача с понятным решением;
- `high` — кросс-модульная задача или новый контур;
- `xhigh` — только для особенно сложной архитектуры, миграции или трудно воспроизводимого дефекта.

### GPT-5.3-Codex-Spark

Применяется для коротких, узких и интерактивных задач:

- точечная правка UI;
- стили и дизайн-токены;
- небольшой React-компонент;
- тексты интерфейса;
- локальный unit/component test;
- небольшой рефакторинг без изменения поведения;
- форматирование документации;
- исправление конкретной lint/typecheck ошибки.

Spark не назначается единственной моделью для:

- архитектурных изменений;
- публичных контрактов;
- миграций;
- security-sensitive parser code;
- очередей и идемпотентности;
- интеграции с 1С;
- больших кросс-модульных PR.

В каждой Spark-задаче обязательно перечислять точные файлы и команды проверок. Успех нельзя выводить только из ответа модели: необходим фактический test output.

### Fallback

Если Spark недоступен из-за preview-доступа или лимитов, используется `GPT-5.3-Codex` с reasoning `low` или `medium` без изменения scope.

## 5. Режим Codex Cloud

В Codex Cloud локальная среда может отличаться от обычного clone разработчика:

- локальная ветка может называться `work`;
- `git remote -v` может быть пуст;
- GitHub CLI может быть не авторизован;
- прямой `git fetch` может быть недоступен;
- публикация выполняется встроенным действием Codex Cloud.

Эти особенности не являются самостоятельной причиной для остановки реализации.

Codex должен:

1. Работать в текущем checkout.
2. Проверить наличие обязательных task-документов.
3. Выполнить реализацию и проверки.
4. Создать локальный commit.
5. Опубликовать изменения встроенным действием Codex Cloud в желаемую ветку.
6. Если публикация временно недоступна, сообщить local commit SHA и сохранить полный результат работы.

Запрещено требовать наличие shell-remote или `gh auth`, если платформа предоставляет собственный механизм публикации.

## 6. Статусы работы

```text
DRAFT → READY → IN_PROGRESS → REVIEW → CHANGES_REQUESTED → READY_TO_MERGE → DONE
```

Дополнительные статусы:

- `BLOCKED_BUSINESS_DECISION`;
- `BLOCKED_ACCESS`;
- `BLOCKED_CONNECTOR_SYNC`;
- `CANCELLED`.

## 7. Правила PR

- Один реализационный PR — одна работа.
- Заголовок начинается с `WORK-NNN`.
- PR содержит ссылку на issue и task card.
- В описании обязательны scope, список файлов, команды и фактические результаты.
- Golden snapshots не обновляются без объяснения.
- Нельзя утверждать, что тесты пройдены, если они не запускались.
- Merge выполняется только после ревью и зелёного CI.
- Подготовительный PR с документацией не считается реализационным PR.

# 1. Целевая топология

См. [ADR-004](../adr/ADR-004-forus-topology.md).

```text
                    ┌─ БП СНЭКС
Единая 1С:УТ 11 ────┼─ БП СНЭКС СИБИРЬ
        │           └─ Центральная 1С:Розница ── региональные узлы ── франчайзи
        ▲
        │ import-package / receipt-package / mapping-sync (HTTPS, polling)
        │
Сервис нормализации (спутник; нет прямого DB 1С)
        ▲
  XLS/XLSX/CSV/XLS прайсы, PDF/XML/EDI накладные
```

BI читает сверенные витрины. Frontol сосуществует до D-34.

Статусы компонентов до выгрузок: `PLANNED | UNVERIFIED | VERIFIED | RETIRED`.

# 2. Контракт выгрузок баз

Выгрузка — вход W-DI, а не часть Git. Обязательный манифест валидируется схемой `contracts/schemas/config-dump-manifest.schema.json`.

26.08.2026: частичный intake `RETAIL_DUMP_01` — XML каталогов Розницы, статус `UNVERIFIED`. См. [research/2026-08-26/dump-intake-RETAIL-XML.md](research/2026-08-26/dump-intake-RETAIL-XML.md). Магазин в этой конфигурации — справочник `СтруктурныеЕдиницы`, не `Магазины`.

Минимальный состав (D-47 уточняет):

| Код базы | Контур | Зачем |
|---|---|---|
| `UT_CENTRAL` | Центральная УТ | Master НСИ, закупки, себестоимость, расширения |
| `UT_LEGACY` и/или `UT_IMPORT` | Старая/импортная УТ | Исторические отчёты, «ДоработкаИмпорта», ПомощникЗакупок |
| `RETAIL_CENTRAL` | Центральная Розница | Цены, права, узлы |
| `RETAIL_REGION_*` | Региональные узлы | Карта магазинов, автономность |
| `BP_SNEX` / `BP_SIBIR` | Бухгалтерия | Обмен, аналитики, непроведённые документы |

Для каждой базы манифест фиксирует: платформу, конфигурацию, релиз, режим поддержки, список расширений, дату среза, метод (`DT` / `CF` / `XML` / `read-only dump`), классификацию, SHA-256, `gitPolicy=DO_NOT_COMMIT_PAYLOAD`.

Разбор выгрузки заполняет, не ломая схему:

- `mdm-object-catalog` — юридические лица, бренды, магазины, склады, кассы, узлы, статусы;
- `extension-passport` — 14 (или фактическое число) расширений;
- `exchange-catalog` — маршруты, расписание, контрольные поля, SLA;
- later: регистры цен, способы обеспечения, виды документов поступления.

Запрещено: класть DT/CF в Git; логировать полный payload; использовать production credentials в CI.

# 3. Доменные спецификации

## 3.1. Управление программой

Реализуется процессом, не кодом сервиса: GOV-001…012, WORK_PROCESS, decision log, environments DEV/TEST/UAT/PROD.

Технический долг репозитория на T0:

- разблокировать GitHub Actions (D-29);
- инвентаризировать stacked PR WORK-006…009 (D-30);
- не считать локальные pytest финальной приёмкой без CI.

## 3.2. НСИ и качество данных

После выгрузок строится таблица соответствий «магазин — подразделение — склад — касса — организация — регион — узел» (MDM-001). До полных выгрузок допустим только каталог со статусом `UNVERIFIED` и пустыми GUID. Гипотеза по XML Розницы: экземпляр точки = элемент `СтруктурныеЕдиницы`.

Правила, уже обязательные без дампа:

- 1С master внутренних GUID (MDM-003);
- GTIN строка, не глобальный ключ (MDM-005);
- ни одна raw-строка не теряется (MDM-010);
- mapping версионируется в 1С (MDM-008).

Упаковки, MOQ и иерархия штука/блок/короб ждут D-03 и пилотных поставщиков.

## 3.3. Интеграции и обмены

Правило INT-002: документ либо проведён, либо в очереди исключений. Запись без проведения не считается успешной загрузкой.

Мониторинг ARC-010: найдено / выгружено / записано / проведено / ошибка, контрольные суммы, retry, SLA.

Сервисный обмен с 1С — только версионированные контракты (INT-007, INT-010). Outbox уже реализован WORK-003 (INT-009).

## 3.4. Прайсы и нормализация

Полная техническая спецификация — SPEC.md. Статус на 25.08.2026:

| Блок | Статус |
|---|---|
| Регистрация файла, SHA-256, MinIO | MERGED (WORK-002) |
| Очередь/outbox | MERGED (WORK-003) |
| Raw workbook protocol | MERGED (WORK-004) |
| XLSX reader | OPEN PR |
| CSV / XLS / profiles / detection | stacked PR |
| Classification, normalize, DQ, package | не начато |
| Пилотные профили | блокировано D-02 |

Golden fixtures остаются синтетическими, пока заказчик не утвердит обезличенные файлы. Production-прайсы не коммитятся.

## 3.5. Закупки и заказ

Сервис заканчивается на `import-package`. 1С:

1. staging (TASK-020);
2. matching workspace (TASK-021);
3. apply цен/упаковок (TASK-022);
4. типовой расчёт потребности и черновик заказа (TASK-023).

«ПомощникЗакупок» функционально раскладывается и заменяется, не переносится as-is (CFG-005, R-26). Формула рекомендации — D-20, не код Codex.

## 3.6. Приёмка

TZ_ADDENDUM_RECEIVING и ADR-002. Маршрут документа (DIRECT_TO_STORE / CENTRAL_WAREHOUSE / RECEIPT_AND_TRANSFER) — D-11/D-12, уточняется объектами выгрузки УТ.

## 3.7. Финансы

Не реализуется во внешнем сервисе. Требования FIN-001…018 задают:

- контрольный маршрут обменов;
- запрет технических закрытий отрицательных остатков;
- ворота закрытия месяца;
- полную себестоимость и P&L по начислению с drill-down;
- казначейство — отдельное решение D-24.

Код сервиса поставляет только прослеживаемые пакеты и статусы. Витрины — после G1/G2.

## 3.8. Продажи и операционное управление

OPS-001…008, SAL-001…012. Ключевой методологический замок — факт продажи (OPS-002, D-44): проведённый документ без отгрузки/чека не является выручкой.

Жизненный цикл заказа клиента, резерв, SLA — 1С/CRM, не сервис нормализации.

## 3.9. BI

BI-001…008, SCL-001…003. Официальный срез обязан показывать состав точек и freshness. Неполный срез помечается; не выдаётся за полный (R-30).

Платформа BI — D-25. До G2 допустим только прототип на контрольных витринах.

## 3.10. Масштабирование розницы

SCL-004…010: чек-лист новой точки, пакет региона, роли, волны, нагрузка, поддержка. Не стартует до G1/G2 (R-29).

## 3.11. Расширения 1С

14 расширений первичного анализа (CFG-001…010). После выгрузки CF сверка имён, активности, закрытого кода, собственных регистров.

Критические: `пр_НоменклатураРасширенныйПремиум`, `ПомощникЗакупок` (закрытый код, собственные данные). Не отключать до инвентаризации данных (R-25).

# 4. Модель данных программы (сервис + каталоги)

Сервисные сущности — SPEC.md §5. Дополнительно, вне PostgreSQL приложения либо в отдельной схеме `program_catalog` (решение реализации на TASK-037):

| Каталог | Ключ | Назначение |
|---|---|---|
| `dump_intake` | intakeId | Манифест выгрузки |
| `onec_base` | baseCode | Карта баз |
| `mdm_object` | objectType+code | Соответствия аналитик |
| `extension` | name+baseCode | Паспорта расширений |

Коммерческие суммы контрольного дня могут храниться только в TEST с RBAC; в Git — синтетический example.

# 5. API и события (программа)

Существующий `/api/v1` не расширяется dump-upload endpoint'ом в production: выгрузки передаются out-of-band (защищённое хранилище / SFTP / выделенный bucket), регистрируется только манифест.

Планируемые внутренние операции (TASK-037, не public OpenAPI до G0):

| Операция | Назначение |
|---|---|
| `registerDumpManifest` | Принять метаданные выгрузки |
| `upsertMdmCatalog` | Загрузить разбор соответствий |
| `upsertExtensionPassports` | Паспорта расширений |
| `upsertExchangeCatalog` | Маршруты обменов |
| `putStoreDayReconciliation` | Протокол G1 |

Idempotency-Key обязателен. Повтор того же digest манифеста не создаёт второй intake.

# 6. Состояния разбора выгрузки

`RECEIVED → QUARANTINE_SCAN → REGISTERED → PARSED_CATALOGS → VERIFIED → ARCHIVED`

Альтернативы: `REJECTED_POLICY` (нет манифеста / gitPolicy нарушен), `BLOCKED_SECRETS`, `PARTIAL` (разобрана часть баз).

Payload после `ARCHIVED` остаётся вне Git. В репозиторий попадают только обезличенные каталоги и checksums.

# 7. Безопасность выгрузок

- классификация `INTERNAL` / `RESTRICTED` / `CONFIDENTIAL`;
- `CONFIDENTIAL` payload никогда не копируется на developer laptop без D-08;
- антивирус/сканер по корпоративному требованию;
- DT/CF не распаковываются на машине с исходящим Git remote без allowlist;
- персональные данные и банковские реквизиты маскируются до попадания в TEST;
- примеры контрактов содержат только синтетические GUID и нулевые/округлённые demo-суммы.

# 8. Тестовая стратегия программы

Дополняет SPEC.md §15:

| Уровень | Новое покрытие |
|---|---|
| Contract | dump-manifest, mdm-catalog, extension-passport, exchange-catalog, store-day-recon, kpi-passport |
| Dump integration | разбор CF списка расширений на синтетическом fixture |
| Reconciliation | контрольный день: counts/sums/analytics |
| 1С | idempotency пакета, matching, apply, receipt, не проведение магазином |
| UAT | G4 заказ, G5 приёмка, G6 P&L |
| Security | попытка закоммитить payload отклоняется политикой; path traversal object key |

Golden snapshot выгрузки не обновляется автоматически.

# 10. Решения, которые нельзя угадывать

Все D-01…D-48, плюс точные имена типовых документов УТ, состав MAXMA, офлайн-режим сканера, RPO/RTO.

Допустимо: подготовить пустые каталоги, JSON Schema, ADR draft, синтетические fixtures.

# 11. Критерии изменения спецификации

Как SPEC.md §23, плюс: появление выгрузки **не** является breaking change, если заполняются optional поля каталогов в пределах major 1.x. Новые обязательные поля каталога — minor, если потребители игнорируют unknown via versioned schema with `additionalProperties: false` на известных объектах: тогда требуется minor schema bump и обновление examples.

Идентификатор схемы каталогов: `1.0.0` на момент v3.0.
